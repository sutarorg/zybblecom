# Zybble launch readiness report — 2026-11-20

## Decision: NOT READY (NO-GO)

The local application quality gate is not a launch gate. The repository still cannot accept a customer video, verify it, generate clips, archive the results, or serve private output. Hosted payment and Auth lifecycles are unverified, and most admin operations do not have server adapters. This is a combination of missing implementation and external configuration—not a failed build. No hosted migrations, test payments, paid jobs or deployments were performed. The [initial audit](launch-readiness-audit.md) records the starting state and official references.

## Security and integration status

- **Supabase:** no hosted account or database operation. Embedded DB tests apply the real SQL, then verify own/other/inactive-account behavior using simulated Auth claims and actual PostgreSQL permissions. They do not certify production JWTs, cookie attributes, GoTrue/PostgREST, email delivery, administrator revocation, or hosted RLS.
- **Dodo:** no external checkout/payment/reversal. SDK verification was exercised offline and wallet behavior in embedded SQL. Checkout remains test-only, opt-in. Before enabling staging, configure `DODO_MODE=test_mode`, `DODO_CHECKOUT_ENABLED=1`, `DODO_PAYMENTS_API_KEY`, `DODO_WEBHOOK_SECRET`, and the six `DODO_PRODUCT_{STARTER,CREATOR,STUDIO}_{INR,USD}` IDs. Use tax-inclusive one-time test products, the staging webhook URL, and stage return origins. Prove actual exact totals, fulfilment, repeats, refunds/disputes, reconciliation and alerts. The current checkout recovery gap is unresolved.
- **R2:** no API or bucket operations. The repository does not yet consume R2 credentials. Implement the private staging bucket adapter first; configure the account endpoint, bucket name and scoped key/secret in server secret storage, exact staging CORS incl. ETag, private signed GETs, and lifecycle cleanup. Exercise actual bytes (single/multipart, verify, seek/download and abort/retry). Do not expose signing keys to browsers.
- **ClipSDK:** no real submission or webhook. No verified dedicated sandbox from the referenced docs; get owner approval for a dedicated provider test account and a small, permission-cleared test file before any potentially billable job. Implement/verify submission with stable idempotency, raw signature checking and correlation, receipt persistence, lease-fenced copy/retry, usage-based settlement and known-job reconciliation. A missing or timed-out response must not release a hold or trigger another paid job.
- **Vercel:** no deployment or environment change. Use an isolated staging origin and secrets, protected preview, reviewed webhook ingress and observability. Verify canonical vs application origin and trusted geo header handling in actual deployment. Don't send debug traces with sensitive data to CI; all generated QA artifacts are from disconnected runs.
