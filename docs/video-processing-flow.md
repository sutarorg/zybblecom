# Video processing: partial integration, not production-ready

The application reads R2 and ClipSDK configuration on the server. Verified, archived clips from completed and settled jobs can obtain short-lived private R2 links in the editor. ClipSDK terminal deliveries for known jobs are verified and recorded for later reconciliation. Administrators can read the provider status of an already correlated job. None of these paths submits or bills a job. The [source upload path](source-uploads.md) is separate from archived clips. There is still no writer that produces archived clips and no automatic reconciliation/archiving worker.

## Isolated staging setup

1. In Cloudflare, open **R2 Object Storage** → select a private staging bucket → copy its name and copy the account ID. Open **Manage R2 API Tokens**, create a token limited to **Object Read Only** on that bucket, then copy its S3 access key ID and secret. Use `R2_ACCOUNT_ID`, `R2_BUCKET_NAME`, `R2_ACCESS_KEY_ID`, and `R2_SECRET_ACCESS_KEY` in the app's staging environment. Disable the public development URL and do not attach a public domain. The current code targets the standard Cloudflare R2 endpoint, not a jurisdiction-specific endpoint.
2. Open the bucket's **Settings → CORS Policy**. Allow `GET` from the exact staging app origin, allow `Range`, and expose `Accept-Ranges`, `Content-Range`, `Content-Length`, and `ETag`. Keep archive metadata private/no-store with the correct media type. Preview links expire after five minutes (refresh the editor for a fresh link); downloads expire after one minute. A signed URL is a temporary bearer grant, not a publicly shareable URL. A browser test with a real isolated archived file remains required.
3. In ClipSDK's project dashboard, use a dedicated test API key and its full `whsec_` signing secret. Store these as `CLIPSDK_API_KEY` and `CLIPSDK_WEBHOOK_SECRET` in the app's staging environment; keep the two values paired. The webhook URL for a **future** authorized submission is `https://<staging-origin>/api/webhooks/clipsdk`; do not point production jobs at it. Apply `20261120000600_clipsdk_receipts.sql` in staging before doing receipt tests. No request was sent to ClipSDK during implementation; a no-charge provider environment has not been established.
4. Use a separately approved staging fixture to prove that a creator can see only their own archived media, other creators receive no grant, range playback and captions work, and duplicate signed ClipSDK receipts leave one pending row without mutating a job or a wallet. Confirm that the administrator status endpoint only returns status/stage for the selected internal job and that creator and revoked-admin sessions are denied.

Official references: [R2 presigned URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/), [R2 CORS](https://developers.cloudflare.com/r2/buckets/cors/), [ClipSDK jobs](https://clipsdk.com/docs/jobs), and [ClipSDK webhooks](https://clipsdk.com/docs/webhooks).

Planned gating sequence:

1. Validate direct [source uploads](source-uploads.md) and cleanup against isolated Cloudflare R2 before enabling them.
2. Dispatch `POST /v1/clips?wait=0` only after credit reservation and trusted input verification. Persist encrypted immutable request bytes, including the source URL, and one stable provider key. Bound dispatch to provider account quotas and honor Retry-After. Unknown state after the idempotency window requires investigation, not another paid job.
3. Verify signed raw webhook bytes before durable receipt; correlate via known job ID, then reconcile against provider status. Archive all required returned assets to private R2 with leases, per-attempt fencing, HTTPS host allowlists, no redirects, and bounded transfer/storage. Mark completion only after stored files are available. Keep clip rank/score/stages only when verified.
4. Exercise direct upload, actual processing, recovery and signed download using a real short MP4 in staging. No claimed latency, codec coverage or provider throughput until measured.
